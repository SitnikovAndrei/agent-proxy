# Правила работы с проектом

Этот документ применяется ко всему репозиторию. Он описывает архитектурные
инварианты и порядок проверки изменений для кодовых агентов и разработчиков.

## Контекст

Проект — самостоятельный Go-прокси OCM + CCM, производный от sing-box, под GPLv3.
Один процесс запускает OpenAI/Codex и/или Anthropic/Claude Code на отдельных
слушателях. На сервис используется один файл credentials; локальные пользователи
авторизуются собственными Bearer-токенами. Usage обоих провайдеров хранится в SQLite.
Не предполагается наличие балансировки аккаунтов, встроенного OAuth-входа или UI.

Перед изменениями прочитайте [README](<README.md>), относящиеся к задаче исходники
и существующие тесты. Реализация — источник истины; несоответствия документации
исправляйте вместе с изменениями поведения. Не переносите автоматически поведение
upstream, если здесь документировано осознанное отличие.

## Карта проекта

| Каталог | Назначение |
| --- | --- |
| `cmd/ocm` | CLI, конфигурация, сигналы и запуск приложения |
| `internal/application` | Совместный lifecycle сервисов и владение общей БД |
| `internal/config` | Строгий JSON, валидация адресов и разделение файловых путей |
| `internal/ocm` | OpenAI/Codex, HTTP/SSE/WebSocket, credentials, модели и тарифы |
| `internal/ccm` | Anthropic, HTTP/SSE, credentials, usage и тарифы |
| `internal/proxy` | Общая авторизация, транспорт, TLS, заголовки, gzip и потоки |
| `internal/persistence` | Атомарная запись, файловые блокировки и отметки ротации |
| `internal/statistics` | SQLite, схема, записи, сводки и HTTP API статистики |
| `_upstream` | Снимок исходников для сверки происхождения; не runtime-код |
| `docs` | Сравнения и аудит переноса |

Модуль и зависимости объявлены в [go.mod](<go.mod>). Конфигурационные примеры:
[OCM-only](<config.example.json>) и [OCM + CCM](<config.combined.example.json>).

## Порядок работы

1. Уточните затрагиваемые протоколы и инварианты; проверьте состояние рабочей копии.
2. Выполняйте минимальные изменения в соответствующем модуле. Не смешивайте
   исправление ошибки с массовым форматированием или обновлением зависимостей.
3. Добавьте регрессионный тест. Используйте существующие тесты OCM как пример
   локального upstream, временных credentials и SQLite.
4. Форматируйте изменённые Go-файлы через `gofmt`, выполните проверки ниже.
5. Обновите документацию и примеры, если изменился пользовательский контракт.
6. В результате перечислите изменения, выполненные проверки и ограничения.
   Не утверждайте совместимость с реальным провайдером без отдельной проверки.

Не отменяйте чужие изменения. Не запускайте рабочий прокси, не меняйте реальные
credentials и не обращайтесь к провайдерам ради тестов без явного запроса.
Не редактируйте `_upstream` как часть обычного исправления; обновление снимка
должно быть отдельной задачей с указанием источника и commit.

## Команды проверки

Нужен Go 1.25 или новее. Выполняйте из корня проекта:

```sh
go mod download
go test ./...
go vet ./...
go test -count=1 -cover ./...
go build -o ocm.exe ./cmd/ocm
```

На Unix можно выбрать имя бинарника `ocm` вместо `ocm.exe`.
Для изменений конкурентного кода дополнительно:

```sh
go test -race ./...
```

Race detector может требовать CGO и C-компилятор. Если запуск недоступен,
сообщите причину, не выдавайте его за пройденный. Обычная сборка SQLite использует
`modernc.org/sqlite` и не требует CGO.
`go mod tidy` используйте при изменении зависимостей; проверяйте изменения
[go.mod](<go.mod>) и [go.sum](<go.sum>), не обновляйте версии без необходимости.

## Инварианты безопасности и протокола

### Авторизация и транспорт

- Локальная авторизация API должна выполняться до чтения/refresh credentials
  и обращения к upstream. `/stats` использует собственную авторизацию.
- Пустой список пользователей разрешает API без авторизации, но не `/stats`.
  Не меняйте это поведение неявно.
- Клиентский токен не должен уходить upstream. Credentials провайдера не должны
  попадать в ответ клиенту, логи, тестовые фикстуры или сообщения об ошибках.
- Не раскрывайте upstream URL с query в ошибках транспорта. Не включайте
  системный HTTP proxy или следование редиректам без отдельной задачи.
- Сохраняйте query string, корректную фильтрацию hop-by-hop заголовков и порядок
  применения клиентских, конфигурационных и серверных заголовков.
- OCM и CCM имеют разные правила заголовков: не унифицируйте их случайно.
  В OCM HTTP и WebSocket должны использовать согласованные серверные identity.
- OAuth OCM не поддерживает chat completions; API key и OAuth имеют разные
  upstream-пути. Не смешивайте эти режимы.

### Credentials и refresh

- Перечитывайте credentials перед новыми запросами/подключениями. Не заменяйте
  это вечным кэшем; уже открытые WebSocket работают со старым аккаунтом.
- Сохраняйте общий deadline refresh, отмену и межпроцессную блокировку.
  Под блокировкой повторно читайте credentials и проверяйте необходимость refresh.
- После успешной ротации сохраняйте токены даже при отмене клиента.
- Сохраняйте неизвестные JSON-поля; перед записью повторно проверяйте credentials,
  чтобы не затереть смену аккаунта или токенов внешним клиентом.
- Не заменяйте атомарную запись обычным `os.WriteFile`. Не ослабляйте fsync,
  права доступа и платформенные гарантии без обоснования.
- Отметка незавершённой ротации предотвращает повторный refresh того же набора
  токенов при неизвестном результате. Не удаляйте её автоматически ради повтора.
  Ответ 4xx от token endpoint — известный исход, при котором отметка очищается.
- Не удаляйте lock-файл работающего процесса. Соблюдение lock внешними CLI
  не гарантировано; копия credentials не является отдельной OAuth-сессией.

### Потоки, usage и остановка

- Учитывайте уже полученный usage до попытки передачи соответствующего события
  клиенту. Сбой записи клиенту не должен терять наблюдавшийся расход.
- Не удваивайте записи при повторных финальных событиях. Не придумывайте usage,
  которого не было в полученных данных провайдера.
- Сохраняйте SSE flush и обработку границ событий между блоками чтения.
- При распаковке gzip удаляйте недействительные заголовки длины и кодировки.
- Неизвестный OpenAI service tier вызывает ошибку учёта, но не должен ломать
  передачу ответа. Тарифы — оценка, не биллинг и не лимиты подписки.
- Ошибка SQLite логируется без подмены ответа провайдера. Запись usage использует
  ограниченный контекст, независимый от отмены клиента.
- Остановка отменяет запросы, закрывает WebSocket и ждёт обработчики; общая БД
  закрывается после завершения остановки сервисов. Не создавайте гонки `Add/Wait`.

### Конфигурация и статистика

- Сохраняйте строгую проверку неизвестных полей, токенов, TLS, смешения плоского
  и секционного форматов, конфликтов слушателей и файловых путей.
- `/stats` ограничен авторизованным пользователем внутри провайдера. Имя должно
  быть непустым и уникальным; чужой scope запрещён.
- SQL-параметры передавайте параметризованно. Не формируйте SQL из пользовательских
  строк и не сохраняйте тела запросов/ответов или секреты в usage.
- Изменения схемы должны учитывать существующие БД. Не удаляйте пользовательские
  записи и не пересчитывайте историческую стоимость без отдельной задачи.

## Тестирование и стиль

- Используйте стандартную библиотеку и существующие зависимости; новые зависимости
  добавляйте только при обоснованной необходимости.
- Держите провайдерскую логику в OCM/CCM, общую — в proxy/persistence/statistics.
  Предпочитайте небольшие функции и явные ошибки, не добавляйте скрытые fallback.
- Для JSON с сохраняемыми неизвестными полями допустим `json.RawMessage`;
  для известного протокола предпочитайте типизированные структуры.
- Тесты должны быть автономными: `httptest`, `t.TempDir`, синтетические токены,
  временные БД; не используйте домашние credentials и рабочие порты.
- Для refresh проверяйте конкуренцию, отмену, deadline, смену файла и сохранение
  после отмены. Для потоков — разбиение событий, дубликаты, gzip и обрыв клиента.
- У CCM, statistics, persistence, proxy и application есть собственные тесты.
  Дополняйте прямые тесты изменяемых контрактов, не полагайтесь исключительно
  на косвенное покрытие OCM.
- Поддерживайте Windows и Unix. Изменения блокировок и атомарной записи проверяйте
  с учётом build tags; тесты одной ОС не доказывают корректность другой.

## Документация и лицензия

Пользовательскую документацию ведите на русском, имена API и кода сохраняйте
в исходном виде. Не фиксируйте в документации случайные результаты покрытия
как постоянные гарантии. Сохраняйте GPLv3 и сведения о происхождении в
[README](<README.md>), [LICENSE](<LICENSE>) и [аудите upstream](<docs/upstream-audit.md>).
Не коммитьте рабочую конфигурацию, credentials, SQLite/WAL/SHM, временные файлы
и собранные бинарники; проверьте [правила игнорирования](<.gitignore>).
