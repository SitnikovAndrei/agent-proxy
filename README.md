# OCM + CCM — прокси для Codex и Claude Code

Один Go-процесс запускает OCM (OpenAI Codex Multiplexer) и CCM (Claude Code
Multiplexer). Клиенты подключаются с собственными токенами, а сервис обращается
к провайдерам с локальными OAuth credentials. OCM поддерживает HTTP, SSE и
WebSocket; CCM — Anthropic HTTP API и SSE. Credentials, порты, пользователи
настраиваются независимо для каждого провайдера. Статистика обоих хранится в общей SQLite-базе.
Таблицы цен перенесены из upstream; это оценка стоимости, а не платёжный отчёт.

## Возможности и навигация

| Сервис | Авторизация у провайдера | Протоколы | Адрес по умолчанию |
| --- | --- | --- | --- |
| OCM | OAuth Codex или OpenAI API key | HTTP, SSE, WebSocket | `127.0.0.1:8080` |
| CCM | OAuth Claude Code | HTTP, SSE | `127.0.0.1:8081` |

Каждый сервис использует один файл credentials; несколько локальных пользователей
разделяются клиентскими токенами. Балансировка между аккаунтами и встроенный OAuth-вход
не реализованы. Перед запуском подготовьте credentials через соответствующий клиент.

## Сборка и запуск

Нужен Go 1.25 или новее, доступный в `PATH`. SQLite не требует CGO.
Команды выполняются из корня проекта. В PowerShell:

```powershell
go mod download
go vet ./...
go test ./...
go build -o ocm.exe ./cmd/ocm
Copy-Item config.example.json config.json
# В config.json замените демонстрационный токен и проверьте credential_path.
.\ocm.exe -c config.json
```

Для совместного запуска вместо плоского примера скопируйте
[комбинированный пример](<config.combined.example.json>). Он явно задаёт
`0.0.0.0` для обоих сервисов: для локального использования замените адреса на
`127.0.0.1`, а оба демонстрационных токена — на собственные случайные секреты.
Не перезаписывайте существующую рабочую конфигурацию без резервной копии.

На Linux/macOS сборка и запуск:

```sh
go build -o ocm ./cmd/ocm
./ocm -c config.json
```

Если Go отсутствует в `PATH`, используйте полный путь к установленному `go`.
`go mod tidy` нужен при изменении зависимостей, а не для обычного запуска.

`-c` по умолчанию указывает на `config.json`. `-version` печатает версию
(по умолчанию `dev`; при сборке можно задать `-ldflags "-X main.version=1.0.0"`).
SIGINT (Ctrl+C) и SIGTERM отменяют активные запросы и закрывают WebSocket-сессии.
Каждый сервис ждёт завершения обработчиков до 30 секунд, затем приложение закрывает SQLite.
Usage записывается сразу, отдельного финального сохранения нет. Файловые операции
credentials не имеют отдельного таймаута.
Если обработчики не завершились вовремя, остановка возвращает ошибку.

## Конфигурация

Неизвестные поля JSON, повторяющиеся или пустые токены пользователей и неполная
TLS-конфигурация отклоняются при загрузке.

Старый плоский формат из `config.example.json` запускает только OCM. Для
совместного запуска используйте `config.combined.example.json`: общий `log_level`
и `database_path` остаются в корне, настройки сервисов находятся в объектах `ocm` и `ccm`.
Можно указать только одну из секций. Отсутствующая секция отключена, `null` вместо
объекта запрещён. Пустой объект включает сервис с настройками по умолчанию.
Смешивать плоские поля и секции нельзя; `log_level` и `database_path` внутри секций запрещены.
`database_path` по умолчанию равен `usage.sqlite`; пустое значение запрещено.
Путь считается от рабочего каталога. Учёт включён для каждого активного провайдера.

По умолчанию OCM слушает `127.0.0.1:8080`, CCM — `127.0.0.1:8081`.
Конфликтующие адреса и пересечения путей credentials, SQLite (включая WAL/SHM) отклоняются.
Учитываются относительные пути, симлинки, а для существующих файлов — жёсткие ссылки.
Если запуск одного сервиса завершается ошибкой, процесс закрывает оба.

Поля секций (в плоском формате `log_level` и `database_path` также находятся в корне):

| Поле | Значение |
| --- | --- |
| `log_level` | Общее поле корня: `debug`, `info`, `warn`, `error`; по умолчанию `info` |
| `database_path` | Общее поле корня: SQLite-база; по умолчанию `usage.sqlite` |
| `listen` | Адрес привязки; по умолчанию `127.0.0.1` |
| `listen_port` | По умолчанию `8080` для OCM, `8081` для CCM; `0` выбирает свободный порт |
| `tls.enabled` | Включает HTTPS; по умолчанию `false` |
| `tls.certificate_path` | PEM-сертификат; обязателен при TLS |
| `tls.key_path` | PEM-ключ; обязателен при TLS |
| `credential_path` | Путь к credentials провайдера; пустое значение включает поиск по умолчанию |
| `users` | Массив `{ "name": "имя", "token": "секрет" }`; токены обязательны и уникальны |
| `headers` | Объект заголовков upstream: значение — строка или массив строк |

При пустом `users` аутентификация клиентов отключена. Иначе клиент передаёт
`Authorization: Bearer <token>` из `users`. Этот токен заменяется на upstream-токен.
Клиентские токены и их части в журнал не записываются.

### OCM

Путь по умолчанию: `$CODEX_HOME/auth.json`, если переменная задана, иначе
`~/.codex/auth.json`. При `SUDO_USER` домашняя папка определяется для этого
пользователя. Относительные пути считаются от текущего рабочего каталога.

`auth.json` с `OPENAI_API_KEY` включает режим API key: путь `/v1/...` сохраняется.
При OAuth (`tokens.access_token`, `tokens.refresh_token`, `tokens.account_id`,
`last_refresh`) `/v1/responses` направляется на Codex backend `/responses`;
POST `/v1/chat/completions` использует адаптер Chat Completions → Responses.
Он переносит system/developer в `instructions`, сообщения и изображения/файлы
в `input`, преобразует function tools, tool calls и их результаты, `tool_choice`,
`reasoning_effort`, `response_format` и `verbosity`. Ответ SSE преобразуется
в chat chunks или собирается в JSON по клиентскому `stream`; `include_usage`
в `stream_options` включает отдельный usage chunk. Responses-подобное тело
с `input` без `messages` также принимается: неизвестные поля сохраняются,
`metadata` и `stream_options` удаляются. Upstream всегда получает
`stream: true` и `store: false`.

В Chat-формате отбрасываются `temperature`, `top_p`, `max_tokens`,
`max_completion_tokens`, `presence_penalty`, `frequency_penalty`, `seed`,
`user`, `metadata`, `store` и прочитанный `stream_options`; пустой/null
`logit_bias` также отбрасывается. Несовместимые параметры дают 400:
`n > 1`, `logprobs: true`, `top_logprobs > 0`, непустой `logit_bias`,
аудио и modalities кроме text, `prediction`, `web_search_options`,
устаревшие `functions`/`function_call`, роль `function`, неизвестные роли,
типы частей/инструментов и верхнеуровневые поля. Неверный JSON, отсутствие
`messages`/`input`, пустой `model` в Chat-формате и сжатое тело запроса также
дают 400; метод кроме POST — 405. API key режим сохраняет прозрачный проксинг.
Совместимость адаптера с реальным Codex backend не гарантируется локальными тестами.

При наличии refresh token и JWT `exp`
OAuth-токен обновляется за 120 секунд до истечения. Срок из JWT имеет приоритет
над `last_refresh`. Если `exp` отсутствует, применяется прежнее правило:
обновление при отсутствии `last_refresh` либо спустя 8 дней. Неверный тип или
неположительный `exp` отклоняется при чтении credentials.
Обновлённые данные атомарно записываются обратно в `auth.json`. OAuth refresh
ограничен 30 секундами вместе с ожиданием блокировки и отменяется при отмене
запроса или остановке сервиса. После успешного refresh запись credentials
выполняется даже при отмене клиента, чтобы не потерять ротированные токены.
Параллельные запросы используют результат одного refresh.
При refresh сохраняются остальные поля `auth.json`, включая неизвестные поля
в корне и внутри `tokens`, вложенные объекты и явные `null`. Обновляются поля
токенов и `last_refresh`; остальные данные берутся из повторно прочитанного файла.

Перед каждым новым запросом и WebSocket-подключением сервис перечитывает
`auth.json`: повторный вход в Codex и смена аккаунта не требуют перезапуска OCM.
Удаление или повреждение файла блокирует новые запросы до восстановления файла.
Уже открытые WebSocket-сессии продолжают работать с прежним аккаунтом.
Перед записью результата refresh сервис повторно читает файл. Если credentials
за это время изменились, он использует актуальный файл и отбрасывает результат
refresh прежнего аккаунта.

В OCM из входящего запроса передаются только
`OAI-Product-SKU`, `Accept`, `Content-Type`, `Content-Encoding`, `Accept-Encoding`
и `OpenAI-Beta`. Остальные клиентские заголовки отбрасываются. `Host` и
WebSocket handshake формируются транспортом для адреса upstream;
`Content-Length` и способ передачи тела определяет HTTP-транспорт.
Для каталога моделей `Accept-Encoding` принудительно равен `identity`.
`Cookie` не передаётся, в том числе из конфигурации OCM.
Администратор может явно добавить другие upstream-заголовки через `ocm.headers`.
Для HTTP и WebSocket `Originator` принудительно равен `Codex Desktop`,
а `User-Agent` — `Codex Desktop/0.162.0-alpha.17.2 (Windows 10.0.26200; x86_64) unknown (codex_chatgpt_android_remote; dev)`.
Эти два значения заменяют входящие и конфигурационные заголовки независимо
от платформы, на которой работает прокси.
Эта фильтрация не меняет правила CCM.

Пользовательские `headers` заменяют одноимённые разрешённые входящие заголовки. Затем сервис
устанавливает `Authorization` и, если имеется, `ChatGPT-Account-Id` из учётных
данных. При OAuth явный `tokens.account_id` имеет приоритет; если он отсутствует,
используется `chatgpt_account_id` из JWT `access_token`. Из секции JWT
`https://api.openai.com/auth` также читается `chatgpt_data_residency`, а при его
отсутствии — `chatgpt_compute_residency`. Регион передаётся в
`x-openai-internal-codex-residency` для HTTP, каталога моделей и WebSocket.
В режиме API key заголовки аккаунта Codex и региона не устанавливаются.
JWT разбирается при чтении серверных credentials; это извлечение метаданных,
а не локальная проверка подписи токена. Непрозрачный токен без точек допустим,
но не содержит локальных метаданных. Повреждённый JWT, неверные типы или
некорректные значения identity вызывают ошибку credentials без вывода токена.
Входящие и конфигурационные `ChatGPT-Account-Id`,
`x-openai-internal-codex-residency` и `X-Api-Key` удаляются: выбор аккаунта
принадлежит серверу. Служебные hop-by-hop заголовки и заголовки, перечисленные
в `Connection`, не передаются. Эти правила действуют для HTTP и WebSocket.
Например: `"headers": {"X-Custom": "value", "X-Multi": ["a", "b"]}`.
Соединения исходящие напрямую; detour и системный HTTP proxy не используются.
Ошибка открытия базы статистики прерывает запуск. Ошибка записи usage
попадает в журнал; ответ провайдера всё равно передаётся клиенту.

`service_tier` разбирается в типизированный уровень: `default`, `auto`, `flex`,
`priority` или `scale`. Отсутствующее, `null` или пустое значение означает `default`.
Неизвестное значение вызывает ошибку учёта: расход ответа пропускается с записью
ошибки в журнал, сам ответ передаётся клиенту.
Значения `auto` и `scale` сохраняются отдельно, при этом оценка стоимости для них
по-прежнему использует стандартные тарифы.

### Конкуренция обновления credentials

OCM и CCM используют системную блокировку файла `<credential_path>.api-proxy.lock`:
`flock` на Unix (включая Linux), `LockFileEx` на Windows. Блокировка удерживается
от повторного чтения credentials до завершения refresh и сохранения результата.
После её получения сервис снова проверяет необходимость обновления. При выходе
из процесса ОС освобождает блокировку; lock-файл остаётся на диске. Время ожидания
входит в общий таймаут refresh — 30 секунд по умолчанию.

Lock-файл содержит отметку незавершённого refresh: SHA-256 access token и refresh
token, без самих токенов. Отметка синхронизируется с диском до запроса к провайдеру
и очищается после записи credentials. Credentials сохраняются через временный
файл с `fsync` и атомарной заменой; Unix также синхронизирует каталог,
Windows использует `MOVEFILE_WRITE_THROUGH`.

При падении процесса, ошибке сети/таймауте или ошибке сохранения результат
refresh может быть неизвестен. В этом случае тот же набор токенов повторно
не используется для refresh: сервис возвращает ошибку credentials и пишет
в журнал `previous credential refresh was not committed`. Нужен новый вход
с получением новых credentials. Автоматического повтора refresh нет.
Если новые токены уже сохранены, оставшаяся отметка старого набора не мешает
использовать новые credentials.

Все копии прокси должны использовать один и тот же файл credentials на локальной
файловой системе. Симлинки разрешаются перед выбором lock-файла. Разные пути
через hard link, отдельные копии файлов и разные машины так не координируются.
Codex CLI и Claude Code не обязаны соблюдать эту блокировку: для независимой
работы нужна отдельная OAuth-сессия прокси. Копирование auth.json не создаёт
новую сессию. Это ограничение не устраняется межпроцессным lock.

Не удаляйте и не заменяйте lock-файл, пока работает хотя бы один процесс прокси:
иначе процессы могут заблокировать разные файлы. Если отметка повреждена,
остановите все процессы, выполните новый вход, удалите повреждённый lock-файл
и запустите прокси. Lock-файл должен быть доступен пользователю сервиса для
создания и записи; пути credentials, SQLite и lock-файлов проверяются на пересечения.

### Каталог моделей OCM

`GET /v1/models` требует тот же клиентский токен, что и остальные API-запросы.
В режиме API key запрос и ответ передаются OpenAI без преобразования.
При OAuth запрос направляется на Codex backend `/models`. Если query-параметр
`client_version` отсутствует, прокси добавляет `client_version=0.162.1`
(версия совместимости каталога). Явно переданное значение сохраняется;
это параметр URL, а не HTTP-заголовок. Изменять `config.json` для этого не нужно.

Успешный OAuth-ответ сохраняет исходный `models[]` с метаданными Codex
без изменения полей и добавляет OpenAI-совместимые `object: "list"` и `data`.
Каждый элемент `data` содержит только стандартные поля:

```json
{"id": "slug-из-каталога", "object": "model", "created": 0, "owned_by": "openai"}
```

Поле `created` равно `0`: Codex не сообщает время создания модели.
Reasoning-метаданные остаются только в исходном `models[]`, если их передал
провайдер: прокси не добавляет `reasoningEfforts`, не вычисляет capability-флаги
и не нормализует дефолты. Конфликты, новые форматы и повторения в этих метаданных
не вызывают 502. Отсутствующие поля не дополняются.

Проверяются корректность JSON, наличие массива `models` (не `null`) и непустой
строковый `slug` у каждой модели. Пустой массив допустим и даёт `data: []`.
Список запрашивается у провайдера, статического списка моделей нет.
Остальные поля исходного JSON сохраняются; существующие корневые `object` и `data`
заменяются совместимым представлением. JSON сериализуется заново, поэтому форматирование
и порядок ключей могут отличаться от исходного ответа.

Заголовки каталога сохраняются за исключением длины, кодировки, контрольных сумм
и ETag исходного тела: `Content-Length`, `Content-Encoding`, `Content-MD5`,
`Digest`, `ETag` удаляются после преобразования. `Content-Type` устанавливается
в `application/json`. HTTP-транспорт может сформировать новую длину ответа.
Ответы с кодом, отличным от 200, передаются без преобразования.
Загрузка каталога ограничена 30 секундами и 8 MiB распакованного тела.
Недоступный или некорректный каталог возвращает 502 без URL upstream в ошибке.

Результат сверки переноса с sing-box: [docs/upstream-audit.md](docs/upstream-audit.md).


## Настройка Codex

В `~/.codex/config.toml`:

```toml
[model_providers.ocm]
name = "OCM"
base_url = "http://127.0.0.1:8080/v1"
wire_api = "responses"
supports_websockets = true
env_key = "OCM_API_KEY"

[profiles.ocm]
model_provider = "ocm"
model = "gpt-5.4"
```

Токен должен совпадать с `users[].token` в конфигурации сервиса:

```powershell
$env:OCM_API_KEY = "replace-with-your-secret-token"
codex --profile ocm
```

## CCM и подключение Claude Code

Путь к credentials: `$CLAUDE_CONFIG_DIR/.credentials.json`, если переменная задана,
иначе `~/.claude/.credentials.json`. При `SUDO_USER` используется домашняя папка
этого пользователя; ошибка определения пользователя прерывает запуск.
Относительные пути считаются от текущего рабочего каталога.
В файле требуется объект `claudeAiOauth` с непустым `accessToken`; `refreshToken`
нужен для обновления, `expiresAt` задаётся в миллисекундах Unix. Нулевая или
отсутствующая дата означает отсутствие автоматического refresh, как в upstream.

CCM перечитывает файл перед каждым запросом и обновляет OAuth за минуту до
истечения срока. Refresh и ожидание другого refresh ограничены 30 секундами и
отменяются вместе с запросом. Успешно полученные токены сохраняются даже при
последующей отмене клиента. Сохраняются посторонние поля файла и OAuth-объекта.
Refresh выполняется под системной межпроцессной блокировкой, описанной в разделе
[о конкуренции обновления credentials](#конкуренция-обновления-credentials).
Перед записью повторно читается файл и сравниваются access token, refresh token
и expiresAt; изменение посторонних полей сохраняется. Если credentials изменились,
результат старого refresh отбрасывается. Внешние клиенты, не соблюдающие блокировку,
всё ещё могут изменить файл между проверкой и атомарной заменой.

На всех платформах эта версия читает файл. Автоматическое чтение macOS Keychain
из sing-box не перенесено; на macOS нужен явный `credential_path` с файловыми
credentials. Встроенного входа через браузер нет: сначала выполните вход в
Claude Code на машине, где работает прокси.

CCM проксирует `/v1/...` на `https://api.anthropic.com`, включая query string.
Он заменяет `Authorization` на OAuth-токен, удаляет `X-Api-Key` и обеспечивает
наличие `oauth-2025-04-20` в `Anthropic-Beta`. Настроенные дополнительные beta-флаги
сохраняются. HTTP-редиректы upstream не выполняются. Системный HTTP proxy и
sing-box detour не используются.

Для запуска двух сервисов:

```powershell
Copy-Item config.combined.example.json config.json
# Замените оба демонстрационных токена и проверьте пути к credentials.
.\ocm.exe -c config.json
```

В клиентском терминале:

```powershell
$env:ANTHROPIC_BASE_URL = "http://127.0.0.1:8081"
$env:ANTHROPIC_AUTH_TOKEN = "replace-with-your-claude-proxy-token"
Remove-Item Env:ANTHROPIC_API_KEY -ErrorAction SilentlyContinue
claude
```

Токен должен совпадать с `ccm.users[].token`. Адрес содержит корень сервиса,
без добавления `/v1`. Для CCM-only конфигурации оставьте в корне `log_level`
и объект `ccm`, удалив секцию `ocm`.

### Статистика CCM

Учитываются успешные ответы `/v1/messages`: число запросов и входных сообщений,
input/output, cache read, cache creation, отдельно запись кэша на 5 минут и 1 час.
Размер контекста определяется по сумме входных и кэшированных токенов и
фактически отправленному beta-флагу `context-1m…`: 200k либо 1M.
Недельный период берётся из `anthropic-ratelimit-unified-7d-reset`.

Usage из JSON-ответа записывается в SQLite до отправки тела клиенту. В SSE данные из `message_start`
и `message_delta` объединяются, а при `message_stop` сохраняются до передачи
события. При обрыве учитываются уже полученные данные; неизвестный дальнейший
расход восстановить невозможно. Повторный `message_stop` не удваивает счётчик.
Gzip распаковывается для учёта, заголовки длины и кодировки сжатого тела удаляются.

Тарифы перенесены из CCM основной ветки sing-box. Стоимость —
условная оценка по API-тарифам, она не отражает списания или лимиты подписки.
Для неизвестной модели сохранён upstream-тариф Sonnet 4.

## HTTP API статистики

`GET /stats` работает на том же адресе и порту, что соответствующий прокси:
OCM на `8080` возвращает OpenAI, CCM на `8081` — Anthropic.
Endpoint читает локальную SQLite-базу и не обращается к провайдеру.

Передайте `Authorization: Bearer <users[].token>`. Токен даёт доступ к данным
своего `users[].name` внутри этого провайдера. Для статистики имя должно быть
непустым и уникальным среди пользователей этого сервиса. Без настроенных
пользователей endpoint недоступен, даже если API прокси работает без авторизации.

Пример PowerShell для OCM:

```powershell
$statsHeaders = @{ Authorization = "Bearer $env:OCM_API_KEY" }
Invoke-RestMethod -Uri "http://127.0.0.1:8080/stats" -Headers $statsHeaders |
    ConvertTo-Json -Depth 6
Invoke-RestMethod -Uri "http://127.0.0.1:8080/stats?from=2026-10-01&to=2026-11-01&model=gpt-5.4" -Headers $statsHeaders |
    ConvertTo-Json -Depth 6
```

Для CCM используйте порт `8081` и токен из `ccm.users`.

| Параметр | Значение |
| --- | --- |
| `from` | Начало периода включительно; `YYYY-MM-DD` или RFC3339 с часовым поясом |
| `to` | Конец периода исключительно; такой же формат |
| `model` | Точное имя модели |
| `user` | Необязательное собственное имя пользователя; чужое имя возвращает 403 |
| `limit` | Размер страницы `by_model`: 1–500, по умолчанию 100 |
| `offset` | Смещение страницы `by_model`: 0–1000000, по умолчанию 0 |

Дата без времени означает полночь UTC. Без периода возвращаются данные за всё
время. Неизвестные, пустые, повторяющиеся параметры и некорректный период
возвращают 400. Прочие методы возвращают 405, неправильный или отсутствующий
токен — 401, пустое или неуникальное имя — 403. При ошибке базы возвращается 500
без раскрытия внутренних деталей.

JSON содержит `provider`, `user`, `totals`, `by_model`, `limit`, `offset`, `has_more`.
В `totals` — число запросов и сообщений, некэшированные входные и выходные токены,
чтение и создание кэша (включая TTL 5 минут/1 час), суммарный вход и оценочная
стоимость в USD. В `by_model` — те же показатели с `model`, `context_window` и
`service_tier` для OpenAI. `totals` относится ко всему отфильтрованному набору,
пагинация действует только на `by_model`. Пустая выборка возвращает нулевые
итоги и пустой массив. Итоги и разбивка читаются в одной транзакции с таймаутом
5 секунд; ответ имеет `Cache-Control: no-store`.

## Просмотр статистики SQLite

В `usage_records` хранится одна строка на наблюдавшийся ответ провайдера.
Содержимое запросов, ответов и токены доступа не сохраняются. Имя пользователя
берётся из `users[].name`; для неименованных клиентов хранится SQL `NULL`.
`provider` равен `openai` или `anthropic`, `service_tier` у Anthropic — `NULL`.
Время новых запросов записывается в UTC.

Базу можно открыть SQLite-клиентом. Готовые представления:

- `usage_by_provider` — итоги отдельно для OCM и CCM;
- `usage_by_user` — итоги по пользователям внутри провайдера;
- `usage_by_model` — модели, service tier и размер контекста;
- `usage_by_day` — дни UTC;
- `usage_by_week` — пользователи и недельные периоды из заголовков провайдера.

При установленном `sqlite3`:

```powershell
sqlite3 -header -column usage.sqlite "SELECT * FROM usage_by_user;"
sqlite3 -header -column usage.sqlite "SELECT * FROM usage_by_day ORDER BY day_utc DESC;"
```

`input_tokens` в SQLite — некэшированный вход для обоих провайдеров.
`cache_read_tokens` и `cache_creation_tokens` хранятся отдельно;
`total_input_tokens` в представлениях — их сумма с некэшированным входом.
`estimated_cost_usd` — оценка по тарифам на момент записи, без округления
каждого ответа до центов. В сводках сумма округляется до 6 знаков.
Обновление таблиц цен не пересчитывает уже сохранённые записи.

SQLite работает в WAL с `synchronous=FULL`. Чтение статистики возможно во время
работы прокси. Записи сериализованы, ожидание блокировки ограничено 3 секундами,
SQL-операция получает контекст на 5 секунд, независимый от отмены клиента.
При ошибке БД usage не сохраняется и ошибка записывается в журнал; автоматического
повтора и очереди в памяти нет. Неизвестный расход после обрыва upstream не восстанавливается.
Для резервной копии работающей базы используйте SQLite backup, а при файловом
копировании сначала остановите прокси: файл `-wal` может содержать новые записи.

## Безопасность и ограничения

- При пустом `users` API прокси доступен без авторизации. Не публикуйте такой
  сервис в сеть; по умолчанию привязка локальная, но комбинированный пример
  явно включает прослушивание всех IPv4-интерфейсов.
- При удалённом доступе используйте TLS и ограничение доступа на уровне сети.
  Локальный HTTP не шифрует клиентские токены и содержимое запросов.
- Credentials и клиентские токены — секреты. Не добавляйте их в Git, журналы,
  тестовые фикстуры и отчёты. Защитите права доступа к файлам и SQLite.
- Прокси не выполняет вход через браузер и не читает macOS Keychain.
  Не делите одну OAuth-сессию с независимо обновляющим токены клиентом;
  копирование файла credentials не создаёт отдельную сессию.
- Расход учитывается только по полученным данным провайдера. Потерянные события
  при обрыве соединения не восстанавливаются; оценка стоимости не является биллингом.
- Нет очереди повторной записи usage при ошибке SQLite. Синхронная запись может
  задерживать передачу ответа, особенно при конкуренции за базу.
- Для обычных тел запросов и отслеживаемых JSON-ответов не везде установлены
  ограничения размера; часть данных буферизуется в памяти. При сетевом размещении
  задавайте лимиты на reverse proxy и контролируйте нагрузку.
- Таблицы цен и версии совместимости требуют сопровождения при изменениях
  upstream. Реальная совместимость с провайдером проверяется отдельно от локальных тестов.

## Разработка

Модуль Go называется `ocm`; исполняемый файл собирается из
[точки входа](<cmd/ocm/main.go>). Правила для кодовых агентов описаны в
[AGENTS.md](<AGENTS.md>).

```powershell
go test ./...
go vet ./...
go test -count=1 -cover ./...
go build -o ocm.exe ./cmd/ocm
```

При изменениях конкурентного кода дополнительно запускайте `go test -race ./...`,
если окружение поддерживает race detector; ему может потребоваться CGO и C-компилятор.
Это не меняет отсутствие требования CGO для обычной сборки.

Основные тесты сейчас находятся в OCM и конфигурации. У CCM, SQLite-хранилища,
общего транспорта, persistence и runtime нет собственных тестовых файлов;
часть общих компонентов проверяется косвенно через OCM.
Для новых исправлений добавляйте регрессионные тесты с локальным `httptest`
upstream и временными credentials/SQLite, без настоящих токенов и запросов
к провайдерам.

### Границы модулей

- `internal/ocm` — протокол, credentials, разбор usage и тарифы OpenAI/Codex.
- `internal/ccm` — протокол, credentials, разбор usage и тарифы Anthropic/Claude Code.
- `internal/proxy` — локальная авторизация, HTTP, TLS, заголовки, gzip и потоки.
- `internal/persistence` — атомарная запись credentials и сравнение JSON.
- `internal/statistics` — SQLite, схема, записи usage и сводки.
- `internal/application` — совместный запуск, откат при ошибке и остановка.

без `Content-Encoding: gzip` и без длины сжатого тела.
